# New API

Сначала прочитай `harness/policies/architecture.md` и `harness/policies/coding.md`. Размещай маршрут в `api` владеющей
фичи; корневой `src/copia/service.py` используй только для сборки приложения. Запросы и ответы
описывай отдельными файлами в `api/models`, не смешивая их с HTTP-обработчиком. Преобразование между API и domain
моделями выноси в `api/mappers`, если оно требуется.
Подключай роутер в корневой точке сборки через явную передачу зависимостей; не импортируй `service.py` из фичи.
Если новый роутер читает объекты, которые тесты или приложение заменяют во время работы, передавай функции получения
зависимостей и вызывай их внутри обработчика. Это относится и к подменяемым функциям выполнения blocking I/O в
thread pool. При ответе с уже существующей HTTP-моделью переиспользуй тот же класс,
не создавая копию контракта в новой фиче.

Перед изменением существующей ручки зафиксируй её path, method, status codes, JSON и OpenAPI-схему. Сохраняй контракт,
если задача явно не требует его изменения. Проверяй HTTP-поведение сфокусированными тестами, затем запускай
`./harness/scripts/check.sh`. Не меняй существующие тесты без `harness/workflows/test-integrity-gate.md`.
