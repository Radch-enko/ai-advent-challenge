# Refactoring

Используй `harness/workflows/refactoring.md` как нормативный workflow.

Определи invariants, зафиксируй before-change evidence, если это практически возможно, внеси минимальное structural
change, применяй `harness/workflows/test-integrity-gate.md` при изменении tests, выполни equivalent after-change
verification и `./harness/scripts/check.sh`, затем сообщи invariant evidence и rollback notes.

Не вноси user-visible behavior changes, не пересекай module boundaries без approval, не скрывай failures и не выполняй
commit/push без явного запроса.

При переносе API-моделей следуй `harness/policies/coding.md`. Переводи внутренние импорты на канонические пути и
сравнивай OpenAPI-схему до и после переноса.

При переводе модуля на feature-first layout следуй `harness/policies/architecture.md`: переноси одну функциональную
область за шаг, обновляй architecture-check для новых путей и переводи потребителей на канонические импорты.
Общие правила хранения и очистки секретов размещай в `storage` и `security`; общие runtime-правила — в `common`.
Не возвращай компоненты в корневые `api`, `domain`, `data`.
Не создавай файлы только с повторными импортами и `__all__`; проверяй отсутствие циклических импортов.
Держи `src/copia/service.py` в пределах 600 строк: размещай фичевую сборку в её папке, сохраняй порядок
регистрации маршрутов и сравнивай OpenAPI-схему после каждого переноса.
Ограниченный по размеру кэш и его правило вытеснения держи в компоненте владеющей фичи; точка сборки только создаёт
экземпляр и передаёт его потребителям. При переносе сохраняй порядок вытеснения и точки очистки кэша.
Если существующие тесты заменяют зависимости в `service.py`, передавай в feature-роутер функции получения этих
зависимостей: обработчик должен получать актуальный объект во время запроса. Подключай роутер на прежнем месте,
сохраняя порядок маршрутов и OpenAPI-схему.
Если переносимый репозиторий делит функцию записи с другим компонентом, вынеси её в отдельный файл `data` и обнови
все внутренние импорты. Сравни прежнюю реализацию и проверь операции чтения и записи тестами до и после.
Перед переносом репозитория проверь, не подменяют ли тесты символы старого модуля (например, `os.replace`).
Перенаправь подмены на определяющий модуль и проверь, что они всё ещё действуют после переноса.
При переносе session-scoped маршрутов передавай общий lifecycle/mutation lock и функции получения подменяемых
репозиториев из точки сборки. Сохраняй порядок маршрутов и старые вызываемые символы `service.py`, если их используют
потребители или тесты; сравнивай OpenAPI до и после.
При разделении маршрутов одной фичи на несколько роутеров подключай их в исходных местах регистрации, чтобы порядок
OpenAPI не менялся. Для удаления сессии сохраняй порядок блокировок: сначала message lock, затем lifecycle lock;
после удаления очищай связанные хранилища и кэши в прежнем порядке.
При переносе доступа к сессии и блокировок сохраняй валидацию session ID, ошибки 422/404, восстановление
прерванного MCP turn только при отсутствии активного turn и освобождение message lock после завершения всех users.
Для memory mutation сохраняй порядок: message lock, затем lifecycle lock; освобождай оба в `finally`.
Подменяемые repository, threadpool, locks и словари бери из точки сборки при вызове; не создавай отдельный lock
для каждого HTTP-роутера. Сверяй send, retry, delete, MCP и конкурентные тесты до и после переноса.
При переносе send/retry передавай подменяемые в `service.py` зависимости через явный runtime factory, который берёт
актуальные объекты во время вызова. Это относится и к фабрикам `Agent` и классификатора памяти. Сохраняй общий
message lock для send, retry и MCP-turn, а также исходные ошибки каждой операции.
Вызов `Agent` и сохранение состояния сессии размещай в `sessions/application`: проверяй существование сессии под
lifecycle lock перед вызовом провайдера и перед сохранением, не удерживая lifecycle lock во время provider I/O.
HTTP-ошибку отсутствующей сессии передавай из API через callback; `application` не должен импортировать FastAPI.
При переносе подготовки long-term memory сохраняй отключение памяти для сессий без профиля и исключение ключей из
sticky facts. При генерации заголовка сохраняй отдельный LLM-вызов и operation log, не добавляй запрос на заголовок
в историю чата; под lifecycle lock повторно проверяй существование сессии и отсутствие заголовка перед записью.
При переносе HTTP-обработки сообщений сохраняй формат ошибок с `agent_log_id` и очистку provider trace, событий и
сообщений памяти перед возвратом клиенту. Для user profile записывай `skipped`, `failed` или `completed` operation;
экранированный prompt валидируй до записи `completed`. Подменяемые логгер, репозиторий и threadpool получай при вызове.
При переносе памяти агента разделяй предметные правила (`domain/services`) и загрузку/сохранение через репозитории
(`application`). Передавай подменяемые репозитории через функции получения, а существующий lifecycle lock и порядок
записи сохраняй в точке вызова. Проверяй send, retry и ошибки классификации до и после переноса.
При извлечении координации из `Agent` сохраняй порядок изменения памяти, событий и контекста: обработчик ошибок должен
охватывать и callback, который обновляет состояние `Agent`. Не выпускай наружу ошибку классификатора или trace.
При переносе runtime orchestration из корневого `api` размещай её в `application` владеющей фичи, если она связывает
domain, data и scheduler или другой внешний runtime. Обновляй импорты и проверяй, что `application` не импортирует
`api`.
При переносе task workflow сохраняй переходы через `TaskStateMachine`, checkpoint после каждого этапа и вызова LLM,
один worker на сессию, а также семантику pause, resume, retry и MCP approval. Передавай подменяемые в `service.py`
зависимости через runtime factory, получая актуальные значения при вызове. Не удерживай lifecycle lock во время
provider I/O; сравни OpenAPI и проверь сценарии планирования, выполнения, валидации и отчёта.
При переносе task-моделей сохраняй один определяющий класс в `tasks/domain/models` и обновляй внутренние импорты.
Для task checkpoint, LLM-call journal и MCP approval сохраняй прежний порядок записи и
используй актуальные зависимости из `service.py` во время вызова. Сверяй identity моделей и OpenAPI до и после.
При переносе MCP turn сохраняй общий session message lock, порядок событий SSE, запись статуса turn в сессию и
освобождение worker в `finally`. Worker размещай в `mcp/application`, HTTP-маршруты и ответные модели — в `mcp/api`;
подтверждение MCP tool для task и обычного turn оставляй доступным через тот же endpoint. Сохраняй старые функции
`service.py` как совместимые точки подмены и сравни OpenAPI до и после.
При переносе разрешения MCP-инструментов сохраняй фильтрацию `enabled_tools`, provider alias, schema инструмента,
ошибки отсутствующего соединения и инструмента. Вызывай blocking lookup через thread pool, а подменяемые discoverer
и репозиторий получай при вызове. При переносе вызова инструмента сохраняй заголовки, `allow_local`, формат результата
и преобразование `McpDiscoveryError`; общие функции в `service.py` оставляй для task, turn и scheduled summary.
При переносе scheduled expense summary сохраняй эксклюзивный профиль `accountant`, один разрешённый инструмент
`search_expenses`, серверные границы периода и последовательное чтение страниц до `next_cursor=null`. Публикуй ответ
после полного чтения, сохраняй MCP audit и `agent_log_id` при успехе и ошибке, санитайзинг ошибок и человекочитаемые
даты. Подменяемые resolver, executor, router и log store получай при вызове; не превращай scheduled report в чат.
При переносе маршрутов обычного агента сохраняй валидацию ровно одного источника настройки (профиль или config),
включение long-term memory только для профильного агента, загрузку актуальных invariants при создании и каждом
сообщении, запрет прямого send для MCP-агента и очистку provider error при включённой памяти. Получай подменяемые
factory, router, repositories и threadpool через runtime factory при вызове. Подключай разнесённые группы маршрутов
в исходных местах, сохраняй старые вызываемые символы `service.py` и сравнивай OpenAPI до и после.
При переносе provider metadata и прямого `/completions` сохраняй provider-agnostic HTTP-модели, прежние коды
ошибок, санитайзинг provider trace и добавление глобальных invariants после пользовательского system prompt.
Прямой completion не создаёт агента и не записывает сессию. Бери router, repository и threadpool из актуальной
точки сборки во время запроса; обновляй внутренние импорты и сохраняй OpenAPI-контракт.
При переносе просмотра agent logs держи один канонический набор HTTP-моделей и mapper в `agent_logs/api`;
остальным фичам передавай тот же класс ответа. Сохраняй проверку доступа к сессии до чтения лога, валидацию ID,
изоляцию логов по session ID, прежние 404/422 и кодирование бинарного тела в base64. Подменяемые store и threadpool
получай при запросе. Обновляй внутренние импорты; функции в `service.py`, используемые как точки подмены,
сохраняй до переноса их потребителей. Сверяй OpenAPI и сценарии хранения.
