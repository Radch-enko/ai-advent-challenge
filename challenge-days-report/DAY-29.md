## Объяснение выбора для демо

**Модель:** `qwen3:4b-instruct-2507` — компактная instruct-модель примерно на 4B параметров. Для дневника нужны следование шаблону, аккуратное извлечение фактов и короткие уточняющие вопросы; большая модель для первого локального варианта увеличила бы требования к памяти и время ответа. Выбор — практичная стартовая гипотеза для этой задачи, а не вывод сравнительного бенчмарка.

**Квантование:** `Q4_K_M` — вариант семейства 4-bit K-quant; средний размер представления Q4_K около 4.5 бит на вес из-за блоковых масштабов и служебных значений. Он уменьшает объём весов и требования к памяти по сравнению с более точными вариантами; `M` обозначает средний вариант квантования. Это компромисс для локального запуска, который ещё предстоит сравнить с другой точностью на той же машине. [Описание схем квантования llama.cpp](https://github.com/ggml-org/llama.cpp/wiki/Tensor-Encoding-Schemes), [модельный тег в Ollama](https://ollama.com/library/qwen3:4b-instruct-2507-q4_K_M).

**Параметры:**

- `temperature: 0.2` — снижает вариативность при заполнении фиксированных секций и формулировании задач, сохраняя естественный язык для уточнений.
- `max_output_tokens: 768` — ограничивает длину одного ответа; этого бюджета должно хватать на короткое уточнение или структурированные правки заметки, не поощряя длинные пересказы.
- `num_ctx: 8192` — оставляет место для шаблона, разговора за день и результата MCP-инструмента, не резервируя чрезмерно длинное окно контекста для короткой сессионной задачи.
- `top_p: 1.0` — не добавляет дополнительного отсечения вероятностных вариантов; вариативность в основном регулирует низкая temperature.
- Управление контекстом профиля выключено: сценарий рассчитан на одну короткую сессию дневника, без дополнительного механизма сжатия истории.

Эти значения — стартовая конфигурация под рабочий сценарий. После прогона одинакового набора входов на одной машине их можно подтвердить или изменить по качеству, задержке и расходу памяти.

## Продуктовая реализация в Copia

Пользователь может рассказать о дне или попросить агента провести короткий опрос. Профиль доступен как `daily_journal`; в настройках MCP добавляется connection с ID `journal`, затем профиль использует `get_daily_journal` и `apply_daily_journal_changes` (`profiles.json:187-194`, `journal-mcp-server/README.md`). Интерфейс агента показывает, что каждый MCP вызов требует отдельного подтверждения (`client/src/features/agents/ui/Agents.tsx:173-176`).

После одобрения записи backend сохраняет Markdown в `CopiaKnowledgeBase/Journal/YYYY-MM-DD.md`. Заголовки и их порядок заданы backend; новые задачи создаются незакрытыми. RAG не обновляется автоматически: пользователь вручную запускает индексацию в разделе «Документы» (`README.md:49-51`).

## Техническая реализация

1. Ollama profile задаёт `copia-daily-journal-q4`, низкую температуру и ограниченный ответ. Modelfile наследует Q4_K_M tag и ограничивает контекст 8192 токенами.
2. Prompt хранится ресурсом Markdown рядом с feature и подгружается `ProfilesRepository` по ссылке из `profiles.json`.
3. MCP server предоставляет два инструмента и отправляет структурированные GET/PATCH запросы в FastAPI. Он не имеет файлового доступа.
4. Backend принимает операции add/replace/remove/complete_task для фиксированных секций. Repository формирует путь только из ISO-даты, проверяет формат, revision и symlinks, затем пишет во временный файл и выполняет атомарную замену.
5. Compose монтирует `CopiaKnowledgeBase` read-only и подключает её `Journal` отдельным writable mount (`compose.yaml:19-31`). Доверенный MCP endpoint добавлен в точный allowlist; отдельная защита прямого HTTP endpoint и изменение OTel body capture не входят в согласованный scope.

В реализации есть новые тесты repository/API, prompt-resource resolution, MCP proxy и Docker endpoint (`tests/test_daily_journal.py`, `tests/test_daily_journal_profile_and_template.py`, `tests/test_mcp_journal_docker_endpoint.py`, `journal-mcp-server/tests/test_server.py`). Результаты автоматических проверок указаны ниже; отдельно подтверждённый пользователем UI-сценарий ограничен созданием заметки в правильной папке.

## Сценарий демо

### Подготовка

1. Создать отдельный каталог для вымышленных данных, чтобы демо не обращалось к личной базе знаний:

   ```bash
   mkdir -p /tmp/copia-day29/CopiaKnowledgeBase/Journal
   ```

2. На Mac mini alias `copia-daily-journal-q4` уже создан и пользователь сообщил об успешном тесте агента. Если нужно повторить настройку без клона репозитория, создать модель из временного Modelfile:

   ```bash
   ollama pull qwen3:4b-instruct-2507-q4_K_M
   cat > /tmp/DailyJournal.Modelfile <<'EOF'
   FROM qwen3:4b-instruct-2507-q4_K_M
   PARAMETER num_ctx 8192
   EOF
   ollama create copia-daily-journal-q4 -f /tmp/DailyJournal.Modelfile
   ```

3. Запустить Copia API и UI по README, задав изолированные пути и `OLLAMA_BASE_URL`, доступный API-процессу:

   ```bash
   COPIA_DATA_ROOT=/tmp/copia-day29-data \
   COPIA_DOCUMENTS_PATH=/tmp/copia-day29 \
   COPIA_JOURNAL_PATH=/tmp/copia-day29/CopiaKnowledgeBase/Journal \
   ./scripts/restart-dev.sh
   ```

4. В отдельном окружении установить `journal-mcp-server` согласно `journal-mcp-server/pyproject.toml`, запустить его с `COPIA_API_URL=http://127.0.0.1:8000` и Streamable HTTP transport. В MCP settings Copia добавить endpoint `http://127.0.0.1:8002/mcp` с ID `journal`. Соединение и доступность двух инструментов показываются на экране MCP settings (`client/src/features/mcp/ui/McpSettingsScreen.tsx:119-145`).

### Запись

1. Открыть агента «Дневник дня» и убедиться, что у него включены только инструменты Journal из MCP connection `journal`. Уже подтверждено пользователем: агент сохранил тестовую заметку в правильную папку. Для демо показать это на изолированном каталоге с вымышленными данными.
2. Передать вымышленное сообщение: «Сегодня проверил тестовый календарь. Заметил, что короткие списки удобнее. Завтра хочу проверить сохранение черновика. Благодарен за спокойный вечер».
3. На запрос `apply_daily_journal_changes` сначала нажать отклонение. Убедиться, что MCP сообщает об отклонении и файл не создан.
4. Повторить сообщение, одобрить предложенный вызов и показать созданный `2026-10-11.md` (или дату текущего дня в `Asia/Omsk`). Проверить неизменный шаблон, пункты в подходящих секциях и незакрытую задачу `- [ ] Проверить сохранение черновика`.
5. Попросить исправить один пункт. Показать отдельное подтверждение чтения, затем изменение с актуальной `revision` и отдельное подтверждение записи. Убедиться, что остальные секции сохранены.
6. После подтверждения показать краткий ответ агента без приписки про RAG. Если демо включает поиск новой заметки, отдельно открыть раздел «Документы» и вручную запустить переиндексацию.

### Сравнение до и после оптимизации

Перед демонстрацией сохранить набор из нескольких одинаковых вымышленных входов: свободный рассказ, опрос по одному вопросу, исправление записи и неоднозначный будущий шаг. Сначала прогнать их на исходном Ollama профиле с его обычным prompt и параметрами, затем на `daily_journal`. Для каждого прохода записать соблюдение шаблона, точность фактов, отсутствие выдуманных задач, необходимость лишних MCP вызовов и понятность вопроса. Не считать заранее заданный ожидаемый ответ результатом живой модели.

На одной машине и при одинаковых входах записать wall-clock время первого ответа и всей записи, скорость генерации, модельную загрузку памяти во время работы и пиковое RAM/VRAM.
