#+ ADR: agent-files-and-file-policy

Дата: 2026-10-18

Статус: Принято (draft)

Контекст
--------

В кодовой базе вводится новая функциональность "agent" — возможность готовить и применять предлагаемую ИИ-агентом правку к файлам репозитория из интерактивной сессии. Для безопасной работы агента необходимо явно определить, какие файлы и расширения агенту позволено читать и/или изменять. Также обнаружилась дублирующаяся логика исключения чувствительных путей в нескольких модулях.

Решение
--------

1. Добавить новую секцию конфигурации [agent.files] с полями:
   - read_roots: список относительных путей (корней) внутри репозитория, которые агент может читать;
   - write_roots: список относительных путей, которые агент может изменять;
   - read_extensions: список допустимых расширений файлов для чтения (например, [.py, .md]);
   - write_extensions: список допустимых расширений для записи.

2. Ввести валидацию этих путей и расширений при загрузке конфигурации: путь должен быть относительным, не содержать "..", не быть абсолютным, не допускать компонент, начинающихся с точки (за исключением самóй точки "."), и не содержать жестко исключённых компонентов (см. ниже). Расширения должны начинаться с точки и содержать алфавитно-цифровые символы.

3. Централизовать логику «жёстких исключений» в модуле code_assistance.file_policy и заменить рассредоточенные локальные списки/функции (HARD_EXCLUDED_COMPONENTS, SECRET_FILE_NAMES, SECRET_FILE_SUFFIXES и т. п.) на единый предикат is_hard_excluded(path: Path) -> bool.

4. Обновить модули, использующие проверку на исключённые пути, чтобы вызывать is_hard_excluded:
   - code_assistance.documents — проверять пути документации и при обходе дерева; бросать исключение при попытке прочитать явно исключённую документацию;
   - code_assistance.git_mcp_server — использовать единый предикат и дополнительно проверять символьные ссылки на любом префиксе пути (чтобы не допустить обхода через symlink); при разрешении пути учитывать OSError/ValueError и возвращать безопасность только если итоговый путь тоже не исключён;
   - прочие места (по коду) — конвергировать на одно место функции проверки.

5. CLI: добавить команду /agent <goal>, которая вызывает подготовку рабочего пространства агента, выводит краткое резюме, показывает diff и с подтверждением пользователя применяет изменения (workspace.apply()). В интерфейсах добавлены вспомогательные сообщения и конфиденциальные уведомления расширены, чтобы указать, что выбранные кодовые фрагменты и часть диффа могут передаваться провайдеру.

6. MCP-клиент: добавить метод diff_entries, возвращающий сырые записи (path, kind, patch) и индикатор усечения вывода (truncated); старый метод diff преобразован, чтобы возвращать GitEvidence с понятными сообщениями, используя diff_entries под капотом.

7. Добавлены новые ошибки (AgentFileError) для явного сигнализирования проблем операций с файлами агента.

Последствия
-----------

- Плюсы:
  - Централизация политики исключения упрощает поддержание списка чувствительных компонентов и уменьшает вероятность рассинхронизации между модулями.
  - Явные ограничения read/write для агента повышают безопасность и делают поведение предсказуемым.
  - Явный шаг подтверждения применения патча даёт пользователю контроль над изменениями.

- Минусы / риски:
  - Неправильная конфигурация [agent.files] (слишком широкие права) может позволить агенту читать/писать нежелательные файлы; наоборот, слишком ограничительные настройки могут сделать функцию бесполезной.
  - Переезд логики исключений в единый модуль требует проверить все места использования, чтобы не пропустить неявные проверки.

Альтернативы, рассмотренные
---------------------------

1. Оставить локальные списки исключений в каждом модуле. Отклонено из-за высокой стоимости поддержки и риска рассинхронизации.

2. Разрешать агенту работать только с явным whitelist-списком отдельных файлов (а не корней и расширений). Отклонено: управление на уровне отдельных файлов неудобно и менее гибко для задач рефакторинга/исправления.

3. Полностью запрещать агенту запись (только подготовка патча без применения). Отклонено: важная цель — облегчить рабочий цикл внесения исправлений; однако такая опция может быть добавлена позже как режим только-оценки.

Миграционные шаги
-----------------

1. Добавить в конфигурационный файл (пример в README) секцию agent.files с корректными значениями для целевых репозиториев.
2. Провести ревью кода на предмет мест, где ранее использовалась локальная логика исключений, и убедиться, что они теперь используют file_policy.is_hard_excluded.
3. Написать юнит-тесты для:
   - валидации агент-конфигурации (положительные и отрицательные кейсы);
   - is_hard_excluded для известных чувствительных случаев;
   - проверок git_mcp_server, чтобы символьные ссылки не позволяли выходить за пределы корня.

Открытые вопросы
-----------------

- Нужна ли тонкая настройка уровней логирования/телеметрии для того, какие фрагменты файлов агент запрашивает у LLM (чтобы диагностировать утечки приватных данных)?
- Следует ли добавлять режим dry-run для /agent, где патч готовится и записывается в отдельный каталог (без применения и без интерактивного подтверждения)?

Ссылки
-------

- Изменения в кодовой базе (diff): добавлены валидация agent.files и использование file_policy.is_hard_excluded во многих местах; CLI расширен командой /agent; MCP-клиент разделил diff на diff_entries + diff.
