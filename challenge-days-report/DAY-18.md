# День 18. Планировщик и фоновые задачи

## Цель дня

По исходному заданию агент должен периодически выполнять операцию, сохранять данные и выдавать сводку. В согласованной реализации расписанием управляет Copia backend, а агент «Бухгалтер» вызывает уже существующий MCP-инструмент `search_expenses` и пишет отчёт через LLM. Оценка ниже основана на текущем рабочем дереве и статическом чтении кода; исполняемые проверки в рамках этого отчёта не запускались.

## Продуктовая реализация в Copia

Пользователь задаёт задачи в `~/.copia/schedules.json` по примеру `schedules.example.json`. В примере «Расходы за сегодняшний день» запускаются каждую минуту, а «Недельная сводка расходов» — каждый понедельник в 00:00 `Asia/Omsk`. Изменения конфигурации применяются после перезапуска API (`README.md:30-36`).

В разделе «Сводки» видны названия включённых задач, время до запуска и `wait`/`progress`/`completed`. Ниже показывается последний **успешно завершённый** ответ агента в Markdown; если последний запуск завершился ошибкой, сообщение показывается отдельно (`client/src/ui/components/SummariesScreen.tsx:81-117`). Кнопка `Logs` открывает запросы и ответы LLM для показанной сводки (`client/src/App.tsx:1285-1290`, `client/src/data/api/copiaApi.ts:464-470`).

## Техническая реализация

1. `ScheduledRunner` читает JSON, регистрирует обработчик по `kind`, вычисляет плановый момент и окно отчёта, ограничивает параллелизм одной копией **каждой** задачи и после рестарта обрабатывает максимум последний пропущенный интервал (`src/copia/api/scheduled_runner.py:110-180,222-263`).
2. Обработчик `expense_summary` создаёт независимый запуск `accountant`, оставляет модели только `search_expenses`, принудительно подставляет вычисленные `occurred_from`/`occurred_to` и разрешает ей передавать `cursor` для следующей страницы (`src/copia/api/service.py:2902-2962`). MCP вызывает backend `GET /expenses`; фильтр применяется после чтения строк Excel (`mcp-server/server.py:129-139`, `src/copia/data/expenses_repository.py:47-61`, `src/copia/domain/services/expense_search.py:6-14`). Поэтому ограничен ответ инструмента, но внутреннее чтение всего workbook не устранено.
3. Агент получает `structured_content.items` и `expense_count`, формирует текст через LLM; код проверяет факт вызова инструмента и завершения пагинации, затем сохраняет ответ и ссылку на agent log (`src/copia/api/service.py:2964-3034`). Последняя просьба пользователя отключила проверку смысловой согласованности: даже неверное утверждение LLM «расходов нет» может быть опубликовано; это зафиксировано в `tests/test_scheduled_report_accuracy.py:62-96`. ISO-даты в готовом тексте заменяются на человекочитаемые в часовой зоне отчёта (`src/copia/domain/services/scheduled_report.py:24-37`).
4. Результат и статус записываются в JSON, а HTTP-запросы LLM — в существующий agent log. API возвращает последние запуски и журнал по точному плановому времени; UI не смешивает лог показанного отчёта с более поздним запуском (`src/copia/data/scheduled_runs_repository.py:36-63`, `src/copia/api/service.py:3234-3294`).

### Цепочка запуска агента и MCP tool

1. В `schedules.example.json:4-8,12-21` обе задачи имеют `kind: "expense_summary"` и `profile: "accountant"`. При старте FastAPI `lifespan` запускает `scheduled_runner` (`src/copia/api/service.py:239-248`); тот регистрирует `run_due` в APScheduler для каждой включённой задачи (`src/copia/api/scheduled_runner.py:159-167`).
2. В плановый момент `run_due` вычисляет границы отчёта и вызывает обработчик через `self.handlers[job.kind](job, period_from, period_to)` (`src/copia/api/scheduled_runner.py:222-248`). Сопоставление `expense_summary` с `_expense_summary_job` задано при создании runner (`src/copia/api/service.py:174-179`). Сам планировщик не вызывает MCP и не содержит финансовой логики.
3. `_expense_summary_job` загружает профиль `accountant`, ограничивает его доступ одним `search_expenses`, находит MCP tool и создаёт `McpToolLoop` (`src/copia/api/service.py:2902-2938,2988-2997`). Затем создаёт отдельный `Agent` и вызывает `agent.ask(..., completion=loop.complete)` (`src/copia/api/service.py:3017-3020`). Это точка, где scheduled job действительно запускает агента с MCP-циклом, а не получает расходы напрямую.
4. `Agent` передаёт сообщения в `loop.complete` (`src/copia/domain/models/agent.py:193-200`). Цикл отправляет LLM описание доступного инструмента; если модель возвращает `tool_calls`, выполняет вызов и добавляет ответ инструмента в историю как сообщение `role: "tool"`, после чего снова обращается к LLM за итогом (`src/copia/domain/services/mcp_tool_loop.py:76-103`).
5. Перед исполнением вызова backend заменяет аргументы модели фактическими `occurred_from`, `occurred_to` и `page_size`; от модели принимает только корректный `cursor` следующей страницы (`src/copia/api/service.py:2940-2961`). `execute` вызывает `_execute_resolved_tool`, который отправляет `call_mcp_tool` на MCP connection (`src/copia/api/service.py:2963-2986,2852-2878`). В журнал записываются уже подставленные backend аргументы (`src/copia/domain/services/mcp_tool_loop.py:105-159`).
6. После ответа LLM обработчик проверяет, что инструмент был вызван и все страницы дочитаны, сохраняет agent log и возвращает текст (`src/copia/api/service.py:3021-3034`). `run_due` отмечает запуск `completed` либо `failed` и записывает JSON (`src/copia/api/scheduled_runner.py:248-263`). Вызов инструмента инициирует модель, поэтому отсутствие вызова не предотвращается заранее: такой запуск завершается ошибкой и не публикует сводку.

## Сценарий демо

### Подготовка

1. В корне проекта подготовить зависимости и локальную конфигурацию по `README.md:14-28`: `./harness/scripts/check-dependencies.sh`, затем `cp .env.example .env` и локально задать ключ выбранного LLM-провайдера. Не показывать значение ключа в записи.
2. Подготовить отдельное окружение MCP server по `mcp-server/README.md:11-16`. Убедиться, что `~/.copia/files/finances.xlsx` содержит лист `Expenses` и заголовки из `src/copia/data/expenses_repository.py:18-30`. Для демонстрации нужна хотя бы одна **тестовая** трата с датой сегодняшнего дня в `Asia/Omsk`. Реальный личный workbook и конфигурации в этом отчёте не просматривались; наличие данных — условие демо.
3. Убедиться, что ID MCP connection — `finances`, так как его использует профиль `accountant` (`profiles.json:57-64`). Если connection ещё не создан, выполнить этот шаг через экран `MCP` после запуска сервера, указав `http://127.0.0.1:8001/mcp` (`docs/mcp-agent-tool-flow.md:105-121`).

### Запуск и запись

1. Запустить Copia командой `./scripts/restart-dev.sh` из корня: API — `http://127.0.0.1:8000`, UI — `http://127.0.0.1:5173` (`README.md:14-28`). В отдельном терминале, из каталога `mcp-server`, запустить `COPIA_API_URL=http://127.0.0.1:8000 .venv/bin/copia-finances-mcp --transport streamable-http` (`mcp-server/README.md:27-34`). Показать в UI, что connection `finances` доступен и содержит `search_expenses`.
2. Поместить пример `schedules.example.json` в `~/.copia/schedules.json` и перезапустить Copia командой `./scripts/restart-dev.sh`; сохранить работающий MCP server. Если расписание уже существует, проверить его содержимое перед заменой: это личная конфигурация вне Git. Для чистого запуска пример применяется только после готовности MCP connection.
3. Открыть «Сводки». Показать две строки задач: минутная дневная задача отсчитывает время до запуска, недельная ожидает понедельника 00:00 по Омску. Дождаться следующего минутного запуска; показать переход статуса и текст сводки с подготовленной тестовой тратой. Markdown и локальная дата должны отображаться читаемо. Точный текст и наличие записи зависят от провайдера и тестовых данных.
4. Под итоговым текстом нажать `Logs`. В правой панели выбрать последний HTTP-вызов, вкладку `Request`, найти сообщение `role: "tool"` и `structured_content.items` с тестовой записью; затем открыть `Response` и сопоставить ответ LLM с опубликованной сводкой. Заголовок авторизации должен быть скрыт существующей redaction (`src/copia/data/providers/http_logging.py:259-267`).

**Checklist записи:** локальные API, UI и MCP server запущены; тестовая дата попадает в сегодняшнее окно `Asia/Omsk`; `finances` подключён; оба статуса видны; дневной отчёт обновился; `Logs` показывает запрос с MCP-результатом и ответ провайдера; ключи, личные траты и содержимое `.env` не попали в кадр. Недельный отчёт без ожидания планового понедельника в таком демо не подтверждается.

## Итог проверки

По статическому evidence согласованная версия Дня 18 реализована: backend планирует задачи, агент вызывает существующий MCP tool, JSON хранит запуски, UI показывает сводку и журнал LLM. Буквально **новый** MCP tool с собственным расписанием не создан по решению пользователя; «24/7» ограничено временем работы одного backend-процесса. Возможна неверная, но опубликованная сводка LLM; фильтрация не исключает полного чтения Excel внутри backend.

В этой проверке **не запускались** tests, build, серверы, MCP discovery и реальный LLM-вызов. Наличие тестов видно в `tests/test_scheduled_summary.py`, `tests/test_scheduled_current_day.py`, `tests/test_scheduled_report_accuracy.py`, `tests/test_scheduled_report_logs.py` и `tests/test_scheduled_summary_updates.py`; их успешность текущий отчёт не подтверждает. Для окончательного подтверждения выполнить `./harness/scripts/check.sh` и записать описанный ручной сценарий с тестовыми данными.
