# День 23 — Фильтрация и реранкинг RAG

## Цель дня

Добавить этапы после векторного поиска: порог similarity и два ограничения top-K, query rewrite и reranker. Показывать в чате источники, которые действительно вошли в контекст LLM.

| --- | --- | --- |
| Настройки top-K до фильтрации, порога similarity и top-K после фильтрации | Выполнено по коду; пользователь вручную подтвердил работу настроек | Настройки доступны в панели запроса при включённом RAG (`client/src/features/configuration/ui/settingsComponents.tsx:149-215`). Базовый RAG — один лучший чанк без настроек фильтрации — был реализован в рамках Дня 22 (`challenge-days-report/DAY-22.md`). В этом отчёте за работу Дня 23 засчитываются только добавленные этапы и их UI.

## Продуктовая реализация в Copia

В панели «Настройки запроса» настройки RAG появляются после включения RAG. Пользователь может задать:

- top-K до фильтрации;
- порог similarity;
- top-K после фильтрации;
- отдельные переключатели query rewrite и reranker.

Настройки передаются при создании сессии и сохраняются через обновление режима RAG (`client/src/data/api/sessionsApi.ts:18-34,44-52`; `src/copia/sessions/api/collection_routes.py:58-72`, `src/copia/sessions/api/settings_routes.py:106-119`). В обычном чате UI показывает только реально использованные источники. При выключенном reranker в контекст входят все прошедшие фильтр чанки; при включённом — выбранный reranker победитель.

## Техническая реализация

1. `RagSettings` хранит оба top-K, порог и переключатели. Retriever сначала выполняет поиск по embedding и ограничивает выдачу значением `top_k_before`, затем фильтрует по `similarity_threshold`, затем ограничивает `top_k_after`.
2. При включённом query rewrite вспомогательный LLM превращает вопрос в поисковую формулировку с учётом контекста. Эмбеддинг строится по переписанному запросу.
3. При включённом reranker отдельный структурированный запрос получает исходный вопрос и прошедшие фильтр кандидаты. В основную генерацию передаётся выбранный чанк; без reranker передаются все кандидаты после фильтрации.
4. В `RagRetrievalResult` отдельно хранятся чанки для контекста и метаданные прошедших фильтр источников. Источник содержит `similarity_score` и `selected_for_context` (`src/copia/common/domain/models/knowledge_source.py:8-13`, `src/copia/document_indexing/domain/models/rag_retrieval_result.py:7-11`). UI использует флаг выбора, чтобы не показывать проигравших reranker как источники ответа.
5. Настройки копируются в состояние Task mode при запуске задачи и применяются к retrieval на этапах вызовов LLM (`src/copia/tasks/api/routes.py:117-127`, `src/copia/tasks/application/task_workflow.py:48-71`).

Ограничение: если после фильтрации остались кандидаты, текущая схема reranker требует выбрать один из них и не поддерживает вариант «ни один не подходит» (`src/copia/document_indexing/application/document_retriever.py:201-224`). Prompt основного RAG просит признать недостаток сведений, но это не является жёсткой гарантией отказа модели от ответа (`src/copia/document_indexing/prompts/rag_context.md:1-4`). Для вопросов, требующих строгого ответа только по базе, полезно добавить явный abstention-критерий и проверить его отдельными примерами.

## Сценарий демо

### Подготовка

1. Следуйте запуску из `README.md`: `./harness/scripts/check-dependencies.sh`, затем `./scripts/restart-dev.sh`. Если локального `.env` ещё нет, создайте его из `.env.example` и задайте ключ настроенного провайдера; существующий `.env` не перезаписывайте. Не показывайте секреты в записи. UI открывается на `http://127.0.0.1:5173`, API — на `http://127.0.0.1:8000`.
2. Для записи подготовьте отдельную папку с вымышленными Markdown-документами, укажите её через `COPIA_DOCUMENTS_PATH` до запуска backend и не используйте личную базу знаний. Например:

   ```markdown
   # Aurora Desktop 3.0
   Aurora Desktop 3.0 выходит каждый четверг. Заметки к релизу публикуются в среду.

   # Поддержка Aurora
   Команда поддержки отвечает по будням с 09:00 до 17:00.
   ```

3. На экране «Документы» проверьте путь к папке, выберите embedding provider/model и дождитесь успешной индексации (`client/src/features/document-indexing/ui/DocumentsScreen.tsx:103-150,156-245`).
4. Если для демонстрации используется SigNoz, заранее проверьте доступность OTLP endpoint. Текущий `compose.yaml` включает capture HTTP body и монтирует пользовательскую базу знаний read-only (`compose.yaml:8-24`); поэтому для записи используйте только синтетические документы и убедитесь, что телеметрия доступна только доверенным пользователям.

### Запись

1. В отдельной чистой сессии задайте baseline: включите RAG, выставьте `Top-K до фильтрации = 10`, `Top-K после фильтрации = 3`, порог `-1.00`, выключите query rewrite и reranker. Задайте вопрос: «В какой день выходит Aurora Desktop 3.0?» Зафиксируйте ответ и показанные источники.
2. В другой чистой сессии отправьте тот же вопрос. Включите query rewrite и reranker, оставьте оба top-K равными `10` и `3`, выберите порог между score релевантного чанка и score отвлекающего чанка, увиденными в результатах. Сравните точность фактов и источники с baseline; не используйте заранее фиксированный порог, так как scores зависят от embedding модели и индекса.
3. Покажите под ответом «Источники», затем раскройте сводку выполнения с chunk ID и similarity. При reranker должен отображаться только чанк, реально отправленный в основной контекст.
4. Для query rewrite создайте две независимые сессии, в обеих сначала спросите про расписание Aurora, затем задайте одинаковый короткий follow-up с местоименной ссылкой, например «А когда публикуют заметки?». Сравните retrieval с rewrite включённым и выключенным.
5. Если SigNoz подключён, откройте соответствующий исходящий OpenAI HTTP exchange и сверьте чанки в request body с источниками в UI. Это дополнительная проверка; она требует настроенного SigNoz/OTLP и включённого body capture.

### Checklist записи

- [ ] Используется отдельная синтетическая папка Markdown, личные документы не попадают в кадр или телеметрию.
- [ ] Индекс успешно завершён, embedding provider/model настроены.
- [ ] Baseline и настроенный режим используют одинаковую модель и одинаковый вопрос в чистых сессиях.
- [ ] Зафиксированы ответы, scores и выбранные источники в обоих режимах.
- [ ] Показаны query rewrite и reranker как независимые переключатели.
- [ ] При включённом reranker UI показывает только чанк, переданный в контекст LLM.
- [ ] Секреты провайдеров не видны; при SigNoz body capture включён только для синтетических данных.

## Итог проверки

Требования фильтрации, двух настроек top-K, query rewrite, reranker и отображения только использованных источников реализованы в текущем worktree. Пользователь вручную подтвердил, что проверил настройки RAG и проследил чанки, попавшие в контекст LLM. Сравнение качества между baseline и режимом с фильтрацией/rewriting в виде парных результатов и оценок пока не зафиксировано, поэтому соответствие этому требованию отмечено как частичное.

Тесты, build, серверы и внешние сервисы в рамках этого отчёта не запускались согласно статическому режиму skill. В репозитории есть базовые тесты RAG (`tests/test_document_retriever.py`, `tests/test_rag_sessions.py`, `tests/test_task_rag.py`), но они не подтверждают прохождение новых настроек и не запускались. Ручное подтверждение пользователя является отдельным свидетельством, а не результатом автоматической проверки в этой сессии.

Статус отражает незакоммиченный worktree относительно `HEAD`. Из-за незакоммиченных изменений отчёт не устанавливает автора и точную дату реализации каждого изменения. Изменения SigNoz/HTTP observability в этом отчёте не засчитываются как часть Дня 23.
