## Продуктовая реализация в Copia

Переключатель **RAG enabled** находится в настройках чата рядом с **Task mode** и доступен для обычной сессии и профильного чата. Новая сессия и старые сохранённые сессии работают с RAG выключенным, пока пользователь его не включит. Значение сохраняется в сессии.

При включённом режиме Copia перед запросом ищет один чанк в локальном структурном индексе. После ответа UI показывает название документа, раздел и путь к файлу; ID чанка доступен в раскрывающейся сводке выполнения. В Task mode ID источника показывается для вызовов модели и шагов. Пользователь подтвердил, что ответ с RAG учитывает контекст выбранного чанка. Экран «Документы», появившийся в предыдущем задании, остаётся способом настроить и запустить индексацию.

## Техническая реализация

1. `DocumentIndexingServiceComposition` разделяет один `IndexArtifactStore` между индексатором и `DocumentRetriever`. Retriever загружает указатель последнего успешного запуска, читает `structure-aware.jsonl`, получает embedding вопроса у provider/model из manifest и выбирает ровно один максимум cosine similarity. Порог похожести не применяется. Markdown frontmatter удаляется перед созданием чанков (`src/copia/document_indexing/domain/chunking/structure_aware.py:127-145`), а загрузчик учитывает `.ignore` (`src/copia/document_indexing/data/document_loader.py:45-89`).
2. Обычный чат выполняет retrieval по пользовательскому сообщению; выбранный фрагмент добавляется к системным сообщениям через существующий context builder. При выключенном RAG embedding-вызов не выполняется. При ошибке поиска запрос к LLM не отправляется.
3. Для Task mode настройка копируется в `TaskState` при запуске. Каждый этап делает свежий поиск: планирование и проверка — по исходной инструкции, шаг исполнения — по инструкции шага, отчёт — по исходной инструкции. Каждый повторный запрос отчёта также проходит retrieval.
4. Текст чанка хранится в локальном JSONL-индексе и добавляется к контексту только для текущего запроса. В транскрипт и ответ API записываются только метаданные источника: `chunk_id`, файл, заголовок и раздел. Полные тексты чанков в отчёт не копируются.

Документы, переданные модели через RAG, отправляются выбранному embedding provider при поиске и выбранному LLM provider в контексте ответа. Это ожидаемая граница обработки для текущей provider-конфигурации Copia.

При использовании Compose учитывайте, что текущий `compose.yaml` включает OpenTelemetry и HTTP body capture (`COPIA_OTEL_ENABLED=true`, `COPIA_OTEL_CAPTURE_HTTP_BODIES=true`). Для демо на личных данных используйте локальный запуск с контролируемой конфигурацией или заранее убедитесь, что telemetry endpoint и хранилище трасс доступны только доверенным пользователям. Секреты провайдеров не включайте в запись.

## Сценарий демо

### Подготовка

1. Запустите локальную разработческую версию по README: `./harness/scripts/check-dependencies.sh`, настройте ключ провайдера в локальном окружении и выполните `./scripts/restart-dev.sh`. Если `.env` отсутствует, README предлагает создать его из `.env.example`; существующий `.env` не перезаписывайте. API и веб-клиент доступны на `http://127.0.0.1:8000` и `http://127.0.0.1:5173` (`README.md:14-30`). Не выводите секреты в кадр.
2. Убедитесь, что каталог документов указывает на локальную базу. Для локального запуска путь можно задать через `COPIA_DOCUMENTS_PATH` (`src/copia/common/configuration.py:15-17,114-116`). В Compose каталог документов подключается read-only (`compose.yaml:6-19`); точный source path проверьте на экране «Документы».
3. На экране «Документы» проверьте путь и список файлов, выберите embedding provider/model, запустите индексацию и дождитесь успешного завершения. `.ignore` базы исключает `Templates/*` и вложенные `README.md`; корневой `INDEX.md` под эти правила не попадает и остаётся кандидатом для индексации.
4. Для запросов с личным контекстом используйте локальную конфигурацию с контролируемыми tracing-настройками. В текущем Compose capture тел запросов включён, поэтому до записи проверьте доступность telemetry endpoint и трасс.

### Запись

1. Откройте обычный чат и покажите переключатель **RAG enabled** рядом с **Task mode**. В первой независимой сессии оставьте RAG выключенным и отправьте один вопрос из локально подготовленного набора.
2. Создайте вторую независимую сессию с теми же LLM provider/model и настройками генерации, включите RAG и отправьте тот же вопрос. Сравните ответы, источник под ответом и chunk ID в сводке. Для каждого вопроса предпочтительны отдельные чистые сессии, чтобы история предыдущих ответов не влияла на сравнение.
3. Повторите сравнение для всех 10 локальных вопросов. Оцените каждый ответ по шкале 0–2: `0` — отсутствует основной факт или есть противоречие; `1` — ответ частичный; `2` — ответ покрывает ожидаемые факты и подтверждён источником. Отдельно отметьте, совпал ли source path/раздел с ожидаемым и появились ли неподтверждённые утверждения.
4. Покажите, что при RAG источники видны под ответом, а chunk ID — в раскрытой сводке. При необходимости отдельно покажите Task mode: включите оба режима в независимой сессии и откройте источники вызовов и шагов.
5. Для демонстрации fail-closed поведения используйте отдельный изолированный data root без индекса: ожидается видимая ошибка retrieval без fallback к обычному LLM-вызову. Не удаляйте пользовательский индекс для демонстрации.

### Checklist записи

- [ ] Индексация подготовленного корпуса успешно завершена.

- [ ] Ответ с RAG показывает файл/раздел; в сводке виден chunk ID.
- [ ] В Task mode видны источники отдельных вызовов и шагов.
- [ ] Источник и раздел сравнены с ожидаемыми; неподтверждённые утверждения отмечены отдельно.
- [ ] В кадре нет секретов и личных HTTP body traces; полные тексты чанков не копируются в отчёт.
